# Homomorphic DES Supervisor Evaluation on ESP32

Privacy-preserving Discrete Event System (DES) supervisor evaluation using
EC-ElGamal homomorphic encryption on an ESP32 microcontroller.

The state vector lives only as encrypted ciphertexts in RAM. The only value
ever decrypted is the single enablement bit (0 or 1) produced by each
homomorphic OR-sum.

---

## What this does

In Supervisory Control Theory, a supervisor observes the current state of a
plant and decides which events to enable or disable. Normally this requires
knowing the current state in plaintext.

This project implements the same computation **homomorphically**: state cells
are encrypted with EC-ElGamal, transitions are applied as ciphertext
permutations, and enablement checks are evaluated by homomorphically OR-ing
the enabled cells and decrypting only the resulting bit. The state
distribution itself is never decrypted on the normal run path.

## How to use

### Step 1 — Generate the header

1. Open `generator_ultrades_mono_lmod_lmodred.ipynb` in Jupyter or Colab.
2. In **Cell 3**, set `PROBLEM` to one of:
   - `small_factory` — two-machine pipeline
   - `extended_small_factory` — three-machine pipeline
   - `fms` — Flexible Manufacturing System (Queiroz & Cury 2000)
3. Run all cells (Kernel → Restart & Run All).
4. The notebook writes `supervisor_data_<PROBLEM>.h` into the current directory.

### Step 2 — Build for ESP32

1. Copy `supervisor_data_<PROBLEM>.h` **and** `sdkconfig.ext` into the same
   folder as the `.ino` sketch.
2. In `homomorphic-esp32-ultrades.ino`, update the include near the top:
   ```cpp
   #include "supervisor_data_fms.h"   // ← change to match your problem
   ```
3. Open the sketch in Arduino IDE, select **ESP32 Dev Module**, leave the
   board options at their defaults (CPU 240 MHz, Flash QIO 80 MHz, partition
   "Default 4MB with spiffs"), and flash.
4. Open Serial Monitor at **115200 baud**.

> `sdkconfig.ext` enables hardware MPI acceleration, NIST-curve fast
> reduction, and the precomputed-G table. These are essential — the firmware
> runs roughly 5× slower without them.

## Available problems

### `small_factory`
Two machines connected by a one-slot buffer.

```
M1 ──e1(start)──► busy ──e2(finish)──► idle
M2 ──e3(start)──► busy ──e4(finish)──► idle
Buf: empty ──e2──► full ──e3──► empty
```

- 4 global events, 1 spec, 1 local-modular supervisor
- Monolithic: 6 states

### `extended_small_factory`
Three machines with two buffers.

```
M1 ──a1/b1──► [B1] ──► M2 ──a2/b2──► [B2] ──► M3 ──a3/b3──►
```

- 6 global events, 2 specs, 2 local-modular supervisors
- Monolithic: 18 states

### `fms` — Flexible Manufacturing System (Queiroz & Cury 2000)
Eight machines (C1, C2, Lathe, Mill, Robot, AM, C3, PD) with eight
buffer/routing specifications. E7 and E8 share events through the plant and
are combined as `E78 = E7 ∥ E8` before synthesis to resolve their conflict.

- 31 global events, 7 specs, 7 local-modular supervisors
- Monolithic: too large for flash (omitted automatically)
- Largest supervisor: S6 with 164 states

## Architecture

### Encryption

Standard EC-ElGamal on **NIST P-192** (secp192r1):

```
Setup:  priv ← random in [1, N-1]
        Y    = priv · G                  (public key)

Enc(m): r    ← random
        c1   = r · G
        c2   = m · G + r · Y             (ciphertext is (c1, c2))

Dec:    m·G  = c2 − priv · c1
        m    = 0 iff m·G is the point at infinity
```

Each ciphertext occupies **50 bytes** (two 25-byte compressed points). The
96-bit security level is well above any feasible attack — the smallest
known classical attack on secp192r1 requires ≈2⁹⁶ operations.

### Homomorphic operations — additions only

EC-ElGamal is **additively homomorphic on the message**:
`Enc(a) + Enc(b)` decrypts to `(a + b)·G`. The runtime path never does
homomorphic multiplication — only point additions, via `mbedtls_ecp_muladd`
with both scalars equal to 1. The only scalar multiplications happen
*inside* `elgamal_enc` (once per cell, at setup) and the final decrypt step
of each row (one per query).

For binary messages, `is_zero(m·G)` is 0 iff `m·G` is the point at infinity,
which only happens when `m ≡ 0 (mod N)`. Since we never sum more than a few
cells, the sum is always far below N, so the homomorphic addition behaves
as a **logical OR** of the summed bits. This is exactly what we need to
ask "is event `gi` enabled in the current state?", since the enable-row's
OR-sum over the state vector equals 1 iff the active state is in the
enabled set.

### State representation

For each supervisor the firmware maintains:

| Field | Type | Purpose |
|---|---|---|
| `enc[n]` | `Ciphertext` (50 B each) | compressed state cells |
| `dec_c1[n]`, `dec_c2[n]` | `mbedtls_ecp_point` | decompressed mirror of `enc` |
| `cached_en[]` | `int8_t` | last decrypted value of each constrained row |
| `changes_if_zero[ev]`, `changes_if_one[ev]` | `vector<uint8_t>` | rows that may flip under event `ev` (precomputed) |

The decompressed mirror is kept in lock-step with `enc` so the hot path
never runs `pt_decompress` (which requires a modular square root).

### Transition

When event `ev` fires:

```
nxt[to]      = enc[from]              for each (from, to) pair of event ev
nxt[s]       = Enc(0)                 for any state s not a transition target
nxt_dec[to]  = mbedtls_ecp_copy(dec[from])
```

No EC arithmetic — just ciphertext copies plus a cheap MPI deep-copy of the
decompressed mirror.

## Optimisations

Five layered optimisations bring the heavy benchmark steps from ~33 s
(naive baseline) to ~1 s on the ESP32:

| # | Optimisation | What it does |
|---|---|---|
| 1 | **Conditional invariance** | At load time, for each `(sup, event, row)` triple we precompute whether the row sum can flip `0→1`, `1→0`, both, or neither under that event. At runtime, only rows whose direction matches the current cached value are re-decrypted. |
| 2 | **Persistent decompressed cache** | Each supervisor stores `mbedtls_ecp_point` mirrors of every cell. `do_transition` updates them via cheap `mbedtls_ecp_copy` instead of running `pt_decompress` on every read in the hot path. |
| 3 | **Skip-`g_zero` summands** | After a transition most cells are byte-equal to the literal global `g_zero` constant. `row_decrypt` skips them entirely — typical rows end up summing 1–2 cells instead of dozens. |
| 4 | **Fused row-sum + decrypt** | A single `mbedtls_ecp_muladd(pm, -priv, c1, 1, c2)` performs the secret scalar mul and the final point add together, eliminating an intermediate point + alloc. |
| 5 | **Dual-core work-unit split** | Phase 1 (main core) applies transitions and enqueues `(sup, row)` work units. Phase 2 splits the queue between both cores via a persistent worker task on core 0 (signalled by semaphore, not respawned per step). |

## Benchmark results

ESP32-WROOM-32 @ 240 MHz with `sdkconfig.ext` active and all five
optimisations enabled. Times are in **milliseconds**.

Two builds are reported: the default (scalar blinding) and the optional
`SECURITY_FULL_RERANDOMIZE=1` build. See *Security notes* below for the
side-channel coverage each one provides.

### `fms` — LOCAL MODULAR (7 supervisors, largest 164 states)
| Metric | Default | FULL_RERANDOMIZE=1 |
|---|---|---|
| Average per step | **1022 ms** | 30 076 ms |
| Min | 240 ms | 2 938 ms |
| Max | 3 912 ms | 51 899 ms |
| Total decrypts (17 steps) | 221 | 349 |

### `fms` — LOCAL MODULAR REDUCED (7 supervisors, largest 13 states)
| Metric | Default | FULL_RERANDOMIZE=1 |
|---|---|---|
| Average per step | **813 ms** | 4 059 ms |
| Min | < 1 ms (cache hit, no decrypts) | 292 ms |
| Max | 2 659 ms | 8 396 ms |
| Total decrypts (17 steps) | 179 | 262 |

All steps pass — HE output matches the cleartext Oracle byte-for-byte in
both modes. The default carries scalar-blinding side-channel resistance at
under 1 % overhead on the ESP32-S3 hardware-MPI path. The
`SECURITY_FULL_RERANDOMIZE` build additionally re-randomises every cell on
each transition (closing the byte-equality and ciphertext-propagation leaks)
at ~5× cost on REDUCED and ~29× on LOCAL MODULAR.

The decrypt count goes UP in the FULL build because the "row is trivially
Enc(0), skip the scalar mul" short-circuit in `row_decrypt` only fires when
cells are byte-equal to the global `g_zero` constant — which they're
deliberately never allowed to be in FULL mode.

### What limits performance

The dominant cost on ESP32 is **EC scalar multiplication via the hardware
MPI peripheral**, which takes ~91 ms per call on secp192r1. The heaviest
FMS steps require ~37 decrypts, so the irreducible floor for those steps
is `37 × 91 ms = 3.4 s`, no matter what the surrounding code does. The
parallel-decrypt split helps only marginally because mbedTLS internally
serialises all scalar muls on the single MPI peripheral.

### Going further: ESP32-S3

The **ESP32-S3** ships with a dedicated ECC accelerator (not just MPI),
which executes secp192r1 scalar mul in roughly **10 ms** instead of **91 ms**
— about 9× faster. With the S3, the same code (no changes required) should
bring REDUCED to ~150 ms/step average and LOCAL MODULAR to ~500 ms/step —
both comfortably under 1 s.

## Security notes

The cryptography itself is solid: textbook EC-ElGamal, a standard NIST
curve, hardware-RNG entropy. The firmware is **research-grade**: with the
default `SECURITY_HARDENED=1` setting, one of three originally-known
side-channels is closed; the other two require physical RAM access.

| # | Channel | Status | If exploited |
|---|---|---|---|
| 1 | Timing / power side-channel on private scalar (no blinding on decrypt) | **Closed by default** in HARDENED mode. Each scalar mul is randomised via per-core CTR-DRBG. | Private-key recovery |
| 2 | `g_zero` byte-equality. Non-active cells are byte-identical to a global `Enc(0)`. | Open. | Reveals active-state index after each transition (requires RAM read access) |
| 3 | Active-ciphertext propagation. The active cell's bytes are copied unchanged across transitions. | Open. | Fingerprints the state trajectory across steps (requires RAM read access over time) |

Closing channels 2 and 3 requires re-randomising every non-target cell on
each transition. On its own this is prohibitively expensive (~3× slower
per step) but becomes tractable with a pre-computed `Enc(0)` pool —
generate ciphertexts during idle time, consume them as a single point-add
per cell during `do_transition`. The current code does **not** include
this; it's left as an extension for users who need the full memory-side-
channel resistance.

For published benchmark numbers and trusted-environment deployments, the
default HARDENED mode is sufficient. For adversarial deployments where the
attacker can read or differentially-probe device RAM, channels 2 and 3
must also be addressed.

### Generated `.h` layout

For each supervisor (prefix `lmN_` for local modular, `lmrN_` for reduced,
`mono_` for monolithic):

| Array | Type | Size | Content |
|---|---|---|---|
| `<prefix>init` | `int8_t` | `n` | one-hot initial state vector |
| `<prefix>enable` | `int8_t` | `ne × n` | flat enablement matrix |
| `<prefix>tcnt` | `uint16_t` | `ne` | `(from,to)` pair count per event |
| `<prefix>trans` | `int16_t` | `2 × Σtcnt` | flat `(from, to)` pairs grouped by event |

The `SupDesc` struct (defined in the `.h`) bundles a name pointer +
num_states + the four array pointers. The firmware iterates
`LMOD_SUPS[0 .. LMOD_COUNT-1]` and `LMOD_RED_SUPS[0 .. LMOD_RED_COUNT-1]`
at runtime.

### Monolithic flash limit

The monolithic supervisor is omitted automatically when its array footprint
would exceed `MONO_FLASH_LIMIT` (default 1.2 MB, matching the default ESP32
APP partition). The firmware uses the `HAS_MONO` macro to skip the
monolithic benchmark when it's not included.

## Key design decisions

**Why EC-ElGamal and not a lattice scheme (BFV / CKKS)?**
EC-ElGamal needs only scalar multiplication and point addition — both
provided by mbedTLS with hardware MPI acceleration. Lattice schemes are
more general (fully homomorphic) but require kilobytes of key material and
are not available in mbedTLS.

**Why secp192r1 instead of secp256r1 or secp256k1?**
On ESP32, secp192r1 hits a sweet spot: smallest standard NIST curve in
mbedTLS (smallest scalar mul) AND benefits from the `MBEDTLS_ECP_NIST_OPTIM`
fast-reduction path. 96-bit security is still well beyond any feasible
attack. Switching to secp256r1 is a one-line change (`#define CURVE` plus
`#define PT_LEN 33`).

**Why only homomorphic addition, no multiplication?**
EC-ElGamal is mathematically only additively homomorphic — homomorphic
multiplication would require a pairing-friendly curve (e.g. BLS12-381)
plus bilinear pairings, which are 10–100× slower per operation and a
completely different scheme. The DES supervisor evaluation needs only OR
operations, which we get from additive HE plus the `is_zero` check.

**Why a persistent decompressed cache?**
`pt_decompress` runs a modular square root (~5–10 ms on ESP32). Without
caching, the hot path does ~1000+ decompresses per heavy step. Storing the
decompressed form once and updating it via `mbedtls_ecp_copy` (essentially
MPI memcpy) eliminates that cost entirely.

**Why PROGMEM C arrays instead of JSON?**
JSON would require runtime parsing into a heap-allocated DOM (~3× the raw
data size). PROGMEM arrays are read directly from flash with
`pgm_read_byte` / `pgm_read_word` — zero heap overhead, zero parse time.
